# 機能仕様書：周辺機器記事 マルチプル自動生成プロダクト

## 1. システム概要・目的
本プロダクトは、すでに作成された「メイン製品記事（親記事）」のテキストやメタ情報を入力とし、親記事の本文と構成を維持した「周辺機器・関連商品記事（子記事）」を複数同時に派生生成するシステムである。

ローカルLLM（MLX / Gemma E4B）またはGeminiの選択した一方は、親製品名と周辺機器名を含む冒頭案内文と、`affiliate_links.txt` の商品紹介文に対する最小限の主語・言い回し調整だけを行う。親製品名を主語にする調整は自然にできる場合のみとし、未調整の原文も合格とする。商品名、URL、型番、数値仕様、価格、商品順は変更せず、見出し変換と本文組立は決定的処理で行う。

また、頻繁に追加・変更が発生する周辺機器の定義や紐付けルールは、RDB（データベース）を使わず、**スプレッドシート（CSV/TSV）やMarkdownファイル**で管理・メンテナンスできる設計とする。


## MLXのツール場所
/Users/user/Library/CloudStorage/OneDrive-個人用/開発/MLX

## 2. 全体構成・データフロー

```
[親記事（メイン製品記事）]
       │
       ▼
[周辺機器抽出 & マスタ照合処理] ◀── [Googleスプレッドシート「周辺機器DB」]
       │ (親記事のキーワード・規格から、生成すべき周辺機器リストを決定)
       ▼
[プロンプト組み立てエンジン] ◀── [記事テンプレート群 (.md)]
       │ (親記事の情報 + 周辺機器情報を組み合わせてプロンプト化)
       ▼
[OneDriveジョブJSONをカテゴリごとに保存]
       │
       ├──► [Googleスプレッドシート「周辺機器DB_LLM」へ1子記事1行を登録]
       ▼
[選択した生成エンジン]
  ├── MLX / Gemma E4B（Macローカル）
  └── Gemini（クラウド）
       │ (選択した一方だけで周辺機器記事を複数生成)
       ▼
[OneDrive 連携構造] ───► [クラウドブログ管理システム]
  ├── 記事ルート/周辺機器/<作成日時_親記事タイトル冒頭20文字>/子記事Markdown（公開本文だけ）
  └── 記事ルート外/管理データJSON ───► (親子関係、ジョブ、SEO管理値を保持)
```


## 2.1 動作の仕様

### ＜UXのおさらい＞
Blog Vercelの左サイドパネルで一件または複数の記事を選択して右クリックし、「周辺機器記事作成」または「周辺機器記事作成（N件）」を選ぶ。ポップアップは各親記事タイトルの直下へ、該当カテゴリ名のチェックボックス行だけをコンパクトに表示する。

### <UX実現のための機能とUIの指定>
・Blog Vercel上の左サイドパネル内の記事を右クリックしたとき、既存コンテキストメニューへ「周辺機器記事作成」を追加する。
・右クリック対象が選択集合に含まれる場合は選択済み全記事を親記事候補とし、含まれない場合は右クリックした一記事だけを対象とする。
・各親記事に属する周辺機器カテゴリを記事タイトル直下へチェックボックス行で表示する。商品数、生成予定タイトル、商品一覧、最大件数案内などの補助文は表示しない。
＜例＞
□充電器
□モバイルバッテリー
□外付けSSD
□ケーブル
・チェックボックスの複数選択後、「MLXで作成」「Geminiで作成」「戻る」「プロンプト歯車」の4操作を表示する。
・作成操作では、選択した「親記事×カテゴリ」ごとにOneDriveジョブJSONと「周辺機器DB_LLM」の一行を登録し、一回の操作を共通バッチIDで束ねる。
・「MLXで作成」は既存のMacローカルMLXを使用し、MLXだけで生成から保存まで完結させる。
・「Geminiで作成」は既存のクラウドAPIを使用し、Geminiだけで生成から保存まで完結させる。
・出力先は、Blog Vercel記事ルート直下の `周辺機器/<YYYYMMDD_HHMM_親記事タイトル冒頭20文字>/` とする。日時はジョブ作成時の日本時間を使い、同じ親記事の複数カテゴリは同じフォルダへ保存する。
・MLX用プロンプトとGemini用プロンプトを分離し、記事ルート外のクラウド管理領域へ保存する。
・「プロンプト歯車」ではエンジンをプルダウンで選択し、各エンジンのプロンプトを個別に表示、編集、保存、削除できるようにする。削除時は確認画面を必須とし、現在使用中の既定プロンプトは代替を指定するまで削除できないようにする。
・生成確認画面には使用するプロンプト名と改訂番号を表示し、ジョブにはその識別子を記録する。ただし記事本文にはプロンプト名、改訂番号、エンジン名を出力しない。
・MLXはE4BなのでGeminiAPIのほうが賢いため、トークン消費の無い賢くない側のMLX側を基本としたいためだ。

尚、MacにしかMLXは搭載していないため、Windowsでは「MLXで作成」を無効表示し、MLXジョブを登録しない。Macで「MLXで作成」を押した場合は、Mac専用URL `blogvercel-mlx://run?batch_id=<UUID>` を介して `/Users/user/Applications/Blog Vercel MLX Launcher.app` を開く。ランチャーはバッチID一件だけを `.command` へ渡し、ワーカーが `周辺機器DB_LLM` から同バッチの未処理ジョブを件数上限なく取得して一件ずつ処理する。

生成進捗には、ジョブ登録、MLX起動待ち、親記事・商品・プロンプト読込、生成、本文検査、OneDrive保存、周辺機器DB_LLM更新、完了・失敗の状態を表示する。未完了中はスピナー、進捗バー、経過時間、最終確認時刻を更新し、MLXワーカーのheartbeatにある現在工程と日本語メッセージを表示する。これにより、ジョブが `記事化` のまま止まっているのか、ローカルMLXが実際に生成中なのかを区別できるようにする。

完了した各ジョブには「OneDriveブラウザで開く」を表示し、OneDriveのWeb画面を別タブで開く。その直下へ「エディターで開く」を表示し、生成結果に保存したOneDrive item IDで本文を取得して、このBlog Vercel上で通常の記事と同じ編集画面へ移動する。

### 記事本文と管理情報の分離

生成する子記事Markdownは公開・編集・note投稿に使う本文専用ファイルとする。Frontmatter、YAML、JSON、SEO管理値、メタディスクリプション管理値、親記事ID、ジョブID、生成エンジン名、モデル名、プロンプト名、改訂番号、採点結果、内部思考、作業ログを子記事Markdownへ書き込まない。

これらの詳細管理情報は記事ルート外の管理用JSONに保存し、ユーザーが確認する作成日時、完了日時、タイトル、進捗、記事リンク、親記事情報だけを「周辺機器DB_LLM」に一覧化する。子記事Markdownの最初の空白でない行は必ず記事タイトルのH1とし、LLM応答をコードフェンスやJSONオブジェクトで包んだ状態では保存しない。余計な情報を検出した場合は、黙って削って保存せず、その生成結果を不合格として同じエンジンで再生成する。

## 3. スプレッドシート・ファイルベースDB仕様

メンテナンス性を最優先とし、周辺機器ルールと記事化進捗は、ユーザーが直接確認・編集できるGoogleスプレッドシートで管理する。記事本文、プロンプト、アフィリエイト商品本文、排他制御をスプレッドシートへ詰め込まず、それぞれの正本を分離する。

### 3.1 周辺機器ルールマスタ（タブ名: `周辺機器DB`）

`周辺機器DB` を、親製品の単語・規格と生成すべき周辺機器カテゴリの対応ルールの唯一の正本とする。ユーザーはこのタブへ直接行を追加・変更できる。`accessory_master.csv` をユーザー管理用の正本として作らない。

| 列 | 内容 |
| --- | --- |
| 親製品検出キーワード | 親記事本文と照合する単語・規格・製品種別 |
| 周辺機器カテゴリID | `battery`、`cable`などの安定した内部ID |
| 周辺機器カテゴリ名 | バッテリー、ケーブルなどのUI表示名 |
| タイトル形式 | `製品名 バッテリーおすすめ：`などのタイトル形式 |
| アフィリエイトセクション | `affiliate_links.txt`の`===battery===`などに対応する名前 |
| デフォルト有効 | 右クリック画面で初期選択するか |
| 使用テンプレートファイル | 使用する周辺機器テンプレート |
| 表示優先度 | チェックボックスの表示順 |

Blog Vercelは実行前に必須列、重複カテゴリID、存在しないアフィリエイトセクション、存在しないテンプレートを検査する。ジョブ作成時には使用した行の値と行内容SHA-256をOneDriveジョブJSONへ複製し、生成途中でシートが変更されても実行内容を変えない。

### 3.2 記事化キュー・進捗一覧（タブ名: `周辺機器DB_LLM`）

`周辺機器DB_LLM` は、GeminiとMLXが何を記事化するかを判断する共通キューであり、ユーザーが作成結果を一覧確認する進捗表でもある。一つの子記事につき一行を登録する。

先頭列は次の順序に固定する。

| 列 | 登録・更新規則 |
| --- | --- |
| 作成日時 | Blog Vercelが子記事ジョブを登録した日時 |
| 完了日時 | 記事保存に成功した日時。失敗時は空欄 |
| 記事タイトル | 生成予定または完成した子記事タイトル |
| 進捗 | `記事化`、`失敗`、`完了`のいずれか |
| 記事URLリンク | 完了時に保存した子記事のOneDriveまたはBlog Vercelリンク |
| 大元記事タイトル | 親記事のタイトル |
| 大元記事リンク | 親記事のOneDriveまたはBlog Vercelリンク |

右側へ運用列として、`対象周辺機器`、`生成エンジン`、`エラー概要`、`ジョブID`、`バッチID`を追加する。ジョブIDとバッチIDは必要に応じて非表示にできるが、削除してはならない。

進捗規則:

1. Blog VercelがOneDriveジョブJSONを確定し、対応行の登録にも成功した時点で `記事化` とする。
2. Geminiは `記事化` かつ `生成エンジン=Gemini`、MLXは `記事化` かつ `生成エンジン=MLX` の行だけを処理候補にする。
3. 処理中もシート上は `記事化` を維持し、詳細な `pending`・`processing` とロックはOneDriveジョブJSONで管理する。
4. 保存成功時は `完了日時`、`進捗=完了`、`記事URLリンク`を更新する。
5. 失敗時は `進捗=失敗`、`エラー概要`を更新し、`完了日時`と`記事URLリンク`は空欄にする。
6. ユーザーが再試行可能な失敗行を `記事化` へ戻した場合は、同じジョブIDの試行回数を増やして再実行する。入力不備など再試行不能な行は理由を表示して処理しない。
7. `完了` 行は自動・手動のどちらのワーカーも再処理しない。

シートはユーザー向け一覧と処理候補の入口であり、記事生成に必要な本文・プロンプト改訂・マスタ行スナップショット・排他ロックはOneDriveジョブJSONを正とする。スプレッドシートだけを根拠に記事内容を再構成しない。

### 3.3 記事プロンプトテンプレート (`/templates/tpl_*.md`)
子記事は周辺機器に全面特化した新規記事として書き直さない。親記事を土台として、タイトル、既存SEO見出し、結論だけを最小限変更する「親記事派生型」とする。

既存ブログの文体・見出しルールは、次のプロンプト群を基準とする。

`/Users/user/Library/CloudStorage/OneDrive-個人用/開発/Blog_Vercel/scripts/pipeline/prompts`

特に `/Users/user/Library/CloudStorage/OneDrive-個人用/開発/Blog_Vercel/scripts/pipeline/prompts/02-editor-prompt.txt` のSEO見出し規則を基礎としつつ、周辺機器子記事ではH1と全H2へ同一のカテゴリ接頭辞を決定的に適用する。

#### 子記事の変更可能範囲

変更してよいのは次の4領域だけとする。

1. H1タイトルの文字列
2. 全H2見出しの文字列
3. H1直後へ追加する、対象周辺機器のおすすめ商品を紹介する旨の短い一文
4. 親記事の最初の `▼` 以降にある最初のAmazon URL行の直後へ追加する専用結論見出しと対象商品群。原文を優先し、自然にできる場合だけ主語・助詞・接続・最小限の言い回しを調整する

上記以外のリード文、各章本文、箇条書き、FAQ、まとめ、既存リンク、見出し階層、章順は親記事から変更しない。周辺機器専用の選び方、比較、メリット、FAQなどを新設しない。

#### タイトル変換ルール

親記事H1から製品名を抽出し、`レビュー`、`比較`、`違い`、`まとめ` などの記事軸を取り除く。H1は親タイトルの題意を引き継がず、次の完全一致形式へ変換する。記事外管理情報に確定済みのブランド名・モデル名があればそれを優先し、複数候補が残る場合は実行前UIで確認してから生成する。

```text
製品名 バッテリーおすすめまとめ
製品名 ケーブルおすすめまとめ
製品名 充電器おすすめまとめ
```

例:

```text
M5 iPad Pro レビュー比較違いまとめ
↓
M5 iPad Pro バッテリーおすすめまとめ
```

#### H2見出し変換ルール

全てのH2を次の形式へ変換する。元見出しに製品名と `レビュー`、`比較`、`違い`、`まとめ` が連続している場合は、その記事軸を取り除いて題意だけを残す。製品名で始まらない `Captions` や動画名なども題意として保持し、同じ接頭辞を付ける。

```text
## 製品名 バッテリーおすすめ: 元見出しの題意
## 製品名 ケーブルおすすめ: 元見出しの題意
## 製品名 充電器おすすめ: 元見出しの題意
```

H2の個数、順序、階層は変えず、H3以下と各見出し直下の本文は親記事のまま維持する。見出し変換はLLMへ任せず、保存前の決定的処理で行う。

#### 周辺機器結論の挿入位置

1. 親記事の最初の `▼` 商品行を検出し、その行以降、次の `▼` または次のH2より前にある最初の `amazon.co.jp` または `amzn.to` URL行を検出する。
2. 検出した最初のAmazon URL行の直後へ `## 製品名 周辺機器名おすすめまとめ：結論` を追加し、その直下へ対象のカテゴリ共通説明文と全商品ブロックを元順で置く。
3. 最初の商品名、説明、Amazon URL、URLより後にある親記事本文、2番目以降の商品ブロック、既存H2、既存リンクは原文と原順を維持する。URLより後に親記事本文がある場合、その本文は新しい周辺機器結論より後へ残る。
4. 最初の商品範囲にAmazon URLがない場合だけ、従来どおり次の `▼` または次のH2直前を安全な代替挿入位置とする。
5. 親記事に `▼` 商品ブロックがない場合は、H1直後の冒頭ブロック末尾、または最初のH2直前へ周辺機器結論を追加する。

#### MLX・Geminiへ渡す子記事プロンプト契約

MLXまたはGeminiには親記事全文の再執筆を依頼しない。選択した一方のエンジンへ、親製品名、カテゴリ名、`affiliate_links.txt` の対象商品群だけを渡し、次の内部データだけを生成させる。

- 親製品名から開始し、周辺機器を探すユーザーへ問いかけ、おすすめ商品と商品情報をまとめて紹介する2文の冒頭案内文
- 各 `▼` 商品ブロックの原文、または自然にできる場合だけ主語と最小限の言い回しを親製品向けに調整した本文

商品名行、URL、型番、容量、出力、価格、数値、商品順は変更禁止とする。元の商品紹介文を最優先で維持し、自然にできる場合だけ、親製品を主語にするための主語、助詞、接続、最小限の言い回しを変更できる。親製品名を含まない原文のままでも合格とする。元文に紹介理由がない場合だけ一文を追加できるが、入力にない仕様、互換性、価格、評価、用途は創作しない。

最終記事は決定的処理で組み立てる。親記事の最初の `▼` 以降にある最初のAmazon URL行の直後へ専用結論見出しを置き、調整済みの全 `▼` ブロックを元の順番で一回だけ挿入する。「おすすめ商品のリンクまとめ」、商品別の追加見出し、Amazonアソシエイト免責文、AI整形・編集の注記は追加しない。

`===battery===`、`===adapter===`、`===cable===` 等の直後から最初の `▼` までにある文章は「カテゴリ共通説明文」として分離する。MLXまたはGeminiは、`おすすめ`を含む行で自然にできる場合だけ主語を親製品名へ切り替える。切り替えない原文のままの説明文も合格とする。原文の各行、空行、箇条書き、判断基準、利用シーン、数値、単位、順番は削除してはならない。原文行を順番どおり保った補足行の追加は許可するが、原文より行数が減る出力は不合格とする。調整済みまたは原文の共通説明文は、専用結論見出し直下で商品群の直前へ一回だけ掲載する。

MLXの各 `▼` 商品ブロックも原文の改行数を減らさず、商品名、URL、数値仕様と原文行を順番どおり保持する。HTMLの `<br>` を記事Markdownへ追加しない。Blog Vercelのプレビューは表示時だけ通常改行を改行として描画し、OneDrive保存本文とnote送信本文は元のMarkdown改行のままとする。

MLXの生成・修正回数は周辺機器記事作成画面の歯車から1回・2回・3回を選び、既定値を1回とする。選択値はブラウザだけでなくOneDriveジョブJSONへ固定し、Mac側ワーカーはジョブの値を使う。2回以上を選び、応答が検査に不合格の場合は、それまでの全エラーを次の回へ渡す。選択回数すべてが不合格の場合は不合格出力を本文に使わず、親製品名から開始する決定的な冒頭文、カテゴリ共通説明文の原文、全商品ブロックの原文で安全な子記事を保存する。記事は `完了` とし、OneDriveジョブJSONとBlog Vercelの生成進捗に「警告あり・出力済み」、各試行のエラー、記事URLを表示する。Geminiは従来どおり最大2回とする。

Blog Vercelの「アフィリンク」管理画面は `===MEMO1===` 等に限定せず、ファイル内の全 `===名前===` セクションを記載順にタブ表示する。`battery`、`adapter`、`cable` の表示名はそれぞれ「バッテリー」、「充電器」、「ケーブル」とし、説明文と商品文を同じタブ内で編集・OneDrive保存できるようにする。

#### 子記事プロンプトの最初のゴール

- 親記事の大部分をそのまま残す。
- 全面的なバッテリー・ケーブル特化記事へ作り直さない。
- H1を完全一致形式へ、全H2を同じカテゴリ接頭辞付き形式へ変換する。
- 冒頭は親製品名から始め、周辺機器を探しているか問いかける1文目と、おすすめ商品と商品情報をあわせて紹介する2文目を追加する。
- 商品紹介文は原文を優先し、自然な場合だけ親製品を主語にする最小限の調整を行う。
- 新たに追加する周辺機器商品リンクを、親記事の最初のAmazon URL行直後に設ける専用結論以外へ置かない。
- 親記事に元から存在するリンクは削除・移動しない。

## 4. 処理ステップ詳細仕様

### Step 1: 親記事の入力とキーワード解析
1. 入力された親記事（Markdownまたはテキスト）から以下を解析・自動抽出する。
   * 製品名 (`{PARENT_TITLE}`)
   * 検出された主要規格・キーワード（例: `USB-C`, `ドラム式洗濯機`, `4K`）
2. Googleスプレッドシートの `周辺機器DB` と照合し、一致した「親製品検出キーワード」に対応する**周辺機器カテゴリリスト（複数）**を取得する。
3. ユーザーが複数記事を選択している場合は記事ごとに候補を表示し、選択した「親記事×カテゴリ」について一子記事一ジョブを登録する。一回の操作は共通バッチIDでまとめる。

### Step 2: 子記事生成プロンプトの動的構築
1. 抽出された周辺機器カテゴリごとに、対応する Markdownテンプレート（`tpl_*.md`）を読み込む。
2. 親記事をH1、冒頭、結論部、H2単位のセクションへ解析し、変更禁止領域のSHA-256を記録する。
3. `affiliate_links.txt` から選択カテゴリの名前付きセクションと全 `▼` ブロックを取得する。
4. テンプレートへ親製品名、カテゴリ名、番号付き商品ブロックを渡す。

### Step 3: 選択エンジンによる子記事複数生成
1. 選択したエンジンは `周辺機器DB_LLM` から自分に割り当てられた `進捗=記事化` の行を取得し、ジョブIDで対応するOneDriveジョブJSONを取得・ロックする。
2. MLXを選んだ場合はMLXだけ、Geminiを選んだ場合はGeminiだけへ、親製品名、カテゴリ名、対象商品ブロックを投入する。
3. 選択エンジンは、冒頭案内文と、原文のまままたは主語・最小限の言い回しだけを調整した商品ブロックを生成する。親記事全文は再生成しない。
4. 決定的処理で親記事を複製し、H1と全H2の文字列を変換し、H1直後へ冒頭案内文を追加する。
5. 親記事の最初の `▼` 以降にある最初のAmazon URL行の直後へ `## 製品名 周辺機器名おすすめまとめ：結論` と、調整済みのカテゴリ共通説明文・全商品ブロックを追加する。リンクまとめは追加しない。
6. SEO管理値や生成時の内部データは管理用JSONへ渡し、完成Markdownには混入させない。

周辺機器子記事では、通常記事用 `/Users/user/Library/CloudStorage/OneDrive-個人用/開発/Blog_Vercel/scripts/pipeline/prompts/04-affiliate-link-manager/insert_affiliate_links.py` を呼ばない。対象カテゴリの新規商品リンクがH2前や記事末尾へ分散することを防ぐためである。親記事に元からあるアフィリエイト本文とURLは、結論外を含めて元の位置と原文を維持する。

### Step 4: ファイル出力・既存システム連携
生成された各子記事Markdownには公開本文だけを保存し、YAML Frontmatterやその他の管理情報を付与しない。管理システムが必要とする親子関係、予約状態、SEO管理値、生成履歴は記事ルート外の管理用JSONへ保存する。

* **保存先**: OneDriveのBlog Vercel記事ルート直下 (`周辺機器/{YYYYMMDD_HHMM_親記事タイトル冒頭20文字}/`)
* **ファイル名形式**: `{親記事ID}_child_{周辺機器カテゴリID}.md`

#### 出力ファイル構造例（`parent001_child_charger.md`）：
```markdown
# 製品名 充電器おすすめまとめ

製品名におすすめの充電器をお探しではありませんか？この記事では、製品名におすすめの充電器と商品情報をあわせて紹介します。

▼親記事に元からある最初の商品ブロック

親記事の既存Amazon URL

## 製品名 充電器おすすめまとめ：結論

原文のまま、または自然にできる場合だけ親製品を主語にする最小限の調整を行った `affiliate_links.txt` の全商品ブロック

## 製品名 充電器おすすめ: 親記事の既存H2題意

（ここから先の本文は親記事のまま維持）
```

保存直前に、最初の空白でない行がH1であること、YAML Frontmatter、JSON包み、内部思考、プロンプト復唱、管理キーが含まれないことを検査する。さらに、見出し数・階層・順序、商品名行、URL、型番、数値仕様、商品順、変更量、リンクまとめ非出力を検査する。LFとCRLFの差は正規化し、内容が同じ商品ブロックを誤って不合格にしない。

保存成功後に `周辺機器DB_LLM` の対応行へ完了日時、`進捗=完了`、記事URLリンクを書き込む。選択したMLX生成回数またはGeminiの最大2回がすべて不合格でも、安全な原文フォールバックを保存できた場合は `進捗=完了` とし、警告と各試行エラーはOneDriveジョブJSONおよびBlog Vercelの生成進捗へ表示する。親記事取得・記事組立・記事保存など安全な記事を保存できない障害では、OneDriveジョブJSONへ詳細を残し、シートを `進捗=失敗` として公開可能なエラー概要だけを書き込む。記事保存後にシート更新だけが失敗した場合は記事を再生成せず、OneDriveジョブへ進捗同期待ちを記録し、同じ完了日時と記事URLでシート更新だけを再試行する。

## 8. SEOキーワード別タイトル派生

### 8.1 起動UIと入力整形

記事の右クリックメニューに「タイトル変更」を表示する。この操作は元記事のファイル名を変更する操作ではなく、一つの元記事から複数のSEOキーワード版Markdownを同じOneDriveフォルダへ派生生成する。

入力欄はGoogle検索結果やスプレッドシートからコピーした複数行を受け付ける。Markdownリンクはリンク表示文字だけを残し、Google検索URLを含む生URL、タブ列の `＋`、行頭・行末の記号、空行、重複、大きな空白を除去する。整形後のキーワードと生成予定タイトルは、ジョブ登録前に一覧表示する。

例:

```text
[insta360 x6 空間キャプチャー](Google検索URL)    ＋
insta360 x6 アクセサリー    Google検索URL
```

を次へ変換する。

```text
insta360 x6 空間キャプチャー
insta360 x6 アクセサリー
```

### 8.2 決定的な見出し変換

一キーワードにつき一記事を作り、H1は `# {キーワード}まとめ` とする。H2からH6までは見出し階層を維持し、`{キーワード}まとめ：{元見出しの題意}` へ変換する。既存の `結論` 見出しがある場合は同じ位置で `## {キーワード}まとめ：結論` に変換する。

既存の `結論` 見出しがない場合は、親記事に元からある最初の `▼` 以降で最初に見つかるAmazon URL行の直後へ `## {キーワード}まとめ：結論` と短い結論文を追加する。Amazon URLがない場合だけ、二番目の `▼` または次の見出しより前を代替位置とする。これにより次の順序を保証する。

```markdown
# {キーワード}まとめ

冒頭文

▼元記事の最初の商品

元記事の最初のAmazon URL

## {キーワード}まとめ：結論

短い結論文

元記事の二番目以降の商品ブロック・既存本文
```

### 8.3 MLXの変更許可範囲

MLXへ記事全文を渡さない。MLXへ渡す値は、元H1、変換先キーワード、H1直後の最初の冒頭段落、結論見出し直下の最初の段落だけとする。MLXの応答は `intro_text` と `conclusion_text` の二項目だけを持つJSON Schemaで拘束する。

見出し変換、結論挿入位置、ファイル名、保存場所はプログラムで決定し、MLXに決めさせない。Amazon商品ブロック、アフィリエイト文章、URL、二つの限定段落以外の本文はMLXの変更対象にしない。

MLXの試行回数は既存の歯車設定にある1回・2回・3回を共用し、既定値を1回とする。複数回設定時は、それまでの全検査エラーを次の試行へ渡す。全試行が不合格でも、見出しだけを決定的に変換し、元の冒頭文と結論文を保持した記事を警告付きで保存する。

### 8.4 ジョブ、保存、検査

`/Users/user/Library/CloudStorage/OneDrive-個人用/開発/Blog_Vercel/api/accessories.js` に `create-title-variants` 操作を追加し、新しいVercel Functionファイルは増やさない。一キーワード一ジョブとして共通バッチIDを割り当て、`周辺機器DB_LLM` に作成日時、記事タイトル、進捗、完成記事リンク、大元記事を記録する。

ローカルワーカー `/Users/user/Library/CloudStorage/OneDrive-個人用/開発/MLX/accessories_worker.py` は `job_type=title_variant` を判定し、既存のMLXサーバーと `/Users/user/Library/CloudStorage/OneDrive-個人用/開発/MLX/start_accessories_worker.command` を使って一件ずつ処理する。

完成Markdownは元記事と同じOneDriveフォルダへ `{キーワード}まとめ.md` で保存する。同名ファイルが存在する場合は上書きせず、そのジョブだけを失敗とし、同じバッチの残りを継続する。

- 記事の本文外に生成ジョブ情報を出力していない。
